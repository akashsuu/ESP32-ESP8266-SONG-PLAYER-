# RF24 requirement for ESP8266 core 2.5.0

## The reliable way: vendored sketch

The folder `NodeMCU_sketch/` contains the complete receiver — sketch, modules
and a patched RF24 (`RF24.h`, `RF24.cpp`, `RF24_config.h`, `nRF24L01.h`,
`printf.h`). Upload **every file in that folder** as tabs into one Web Editor
sketch; no library import is involved, so the build cannot pick the wrong RF24.

## The zip way (fallback)

Import [`RF24-1.4.6-ESP8266-2.5.0.zip`](RF24-1.4.6-ESP8266-2.5.0.zip) via
*Libraries* → *Add .ZIP*. It is RF24 by TMRh20 v1.4.6 with one
ESP8266-core-2.5.0-only compatibility change already applied.

> The Web Editor can silently keep using a stale, unpatched RF24 copy even
> after the import — in testing it kept resolving to an unpatched RF24 in
> `directories-user/libraries` and `directories-data/internal`, re-raising the
> `pgm_read_ptr()` compile error. If you hit this, remove every other RF24
> copy and re-import, or use the vendored sketch above.

RF24 releases before 1.4.6 call the ESP8266 2.5.0 `pgm_read_ptr()` macro in a
way that fails to compile with:

```text
'const void*' is not a pointer-to-object type
```

The RF24 upstream project fixed that exact problem in v1.4.6 (pull request
#864). The fix is in RF24 diagnostic implementations such as `printDetails()`,
`printPrettyDetails()`, and `sprintfPrettyDetails()`; it does not change radio
transmission, reception, packet contents, SPI configuration, auto-ACK, or ACK
payload behavior.

The receiver does not call any of the diagnostic functions.

## Arduino Web Editor

1. Use the vendored `NodeMCU_sketch/` folder (recommended), or
   download the included `RF24-1.4.6-ESP8266-2.5.0.zip` file and import it via
   **Import library**.
2. Remove/disable any older RF24 copy associated with the sketch, then compile.

The fix overrides `pgm_read_ptr()` only when `ARDUINO_ARCH_ESP8266` is defined.
It changes only diagnostic PROGMEM pointer handling, not RF24's SPI/radio
behavior, and does not affect AVR or ESP32.
